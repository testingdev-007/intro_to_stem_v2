trackPoint(height) is a real, pre-built LoomSTEM action — not something you wrote yourself, a tool the language gives you. Behind every call, it runs new speed² = old speed² + 2 × gravity × (old height − new height), chained from wherever the cart already was. Thrill is that real physics number — the total of how much speed changes at each point. 🎉 Five real track points. Three lines of code. That's the actual point of a loop.

    
Here's what genuinely happened: repeat 5 times { } ran the two lines inside it five separate times, and because height changed by 15 on every pass, each of those five runs used a different number without you writing five different blocks. That's not a trick specific to rollercoasters — it's the same reason a loop can build a 5-point track or a 500-point one from the same three lines.

    
repeat 5 times {
  trackPoint(height)
  height = height - 15
}

    
Compare that to what you did in the warm-up: four separate blocks, four separate numbers, no way to scale it up without dragging in a fifth, sixth, seventh block by hand. The loop version doesn't just save typing — it means the SHAPE of the track (how many points, how steep) becomes something you can control with two numbers instead of rebuilding the whole thing block by block. That's what you just did in the playground.

    
Underneath, every point still runs the exact same real physics as before — trackPoint() still calls the real formula (new speed² = old speed² + 2 × gravity × (old height − new height)) every single time the loop calls it, five times over, not once. The loop changes how many times the formula runs and with what numbers — it never changes what the formula actually does.

    
One more thing worth noticing: every script here still started with @engine: physics — a genuine, checked declaration, not decoration. Try the sandbox's engine dropdown with something other than "physics" and press Run: it won't silently do nothing, it'll tell you exactly why trackPoint() doesn't belong there. This is a prototype — most LoomSTEM programs don't have this line yet — but it's how a real, deliberately-declared engine boundary would work, loops or no loops.
